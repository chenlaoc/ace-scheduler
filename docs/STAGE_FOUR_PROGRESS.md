## 已实现的使用流程

1. 以 `--monitor-only` 只读启动，进入“实验对照”。磁盘采集默认关闭，不保存为下次启动自动启用的设置。
2. 勾选“启用磁盘记录”，等待探测后选择设备。设备选择只用于新会话；已有会话保留原设备身份。
3. 选择进程实例，填写场景名称和备注，点击“开始基线”。记录过程中修改场景后点击“保存场景信息”。
4. 用“记录时间标记”记录进入游戏、加载、对局、卡顿，也可输入自定义文字。标记不会开始应用后窗口，也不会触发调度。
5. 若需调度实验，由用户到策略页明确应用。结束后保存 JSON；重新打开为只读快照。CSV 包含场景、时钟、设备信息、磁盘样本和操作事件。

磁盘可选采集不影响原有进程监控、策略、恢复及维护。暂停磁盘采集、设备消失或映射变化后，原会话的磁盘记录停止续接，保留原因和已记录数据；重新选择后开始新会话。

## 指标、身份和时钟

- 使用 `PdhAddEnglishCounterW` 添加语言无关的 PhysicalDisk 计数器。每次检查 collect、format、CStatus 和原始累计计数器回退，首次采样、失败、超时、重置保留缺口。
- 记录读写 bytes/s、读写 IOPS、平均读写 seconds/request、平均队列与当前队列。界面吞吐显示十进制 MB/s，延迟显示 ms/request。
- 延迟汇总按区间请求速率乘有效区间时长加权，属于估计请求权重。无请求时延迟为空，真实零延迟仍为零。不生成或宣称单次 I/O 延迟 P95。
- 当前队列是瞬时点，只报告点数与采样最大值，不将其积分成平均队列。各平均指标显示独立有效覆盖；无请求延迟的时间不算有效延迟覆盖。
- 设备描述由只读 `IOCTL_STORAGE_QUERY_PROPERTY` 获取；仅保存型号及序列号衍生哈希，不保存原始序列号。每次采样核对身份，无法核验时记录缺口。每 30 秒重新枚举；失效身份不续接。
- 盘符用 `IOCTL_VOLUME_GET_VOLUME_DISK_EXTENTS` 核验。只枚举有盘符的卷，跨盘或无法映射均明确注明；不能据此推断目录挂载点、Storage Spaces 等全部物理关系。
- 设备负载是系统设备总体数据，不归因到被选进程。进程 I/O 和物理磁盘指标保持分开。
- 本机会话保存单调时间、QPC / 频率、UTC、排除睡眠的活动时钟，以及配对时间误差上界。误差包含单调时钟分辨率，不代表系统 UTC 的绝对准确度。
- 每 30 秒保留锚点；UTC 跳变、长采样暂停、疑似睡眠恢复立即记录断点。与断点区间交叉的速率样本不参与统计。实际系统睡眠仍待人工验收，不能用夹具冒充。
- schema 2 读取 schema 1；旧会话保留“固定 UTC 偏移、近似对齐”，不补造 QPC 或精确锚点。现有 CSV 的 `sample_utc_approx` 仍为近似 UTC，精确配对信息在 metadata 内。

## 并发、容量与保存

PDH 在应用自行创建的独立只读子进程运行，1 秒采集一次，供所有会话共享。单个原子快照邮箱上限 256 KiB，GUI 每 250 ms 检查更新，8 秒无响应停止该子进程；不会终止目标游戏或 ACE。首次探测也计入超时。采样丢帧保留缺口。

磁盘原始记录使用共享临时 SQLite 存储，不按会话复制进内存列表。在线存储最多 100000 条 / 64 MiB、数据库缓存 2 MiB、最多 16 个设备；达到上限显式停止新增采集，不静默淘汰旧样本。正常退出关闭连接后删除临时文件；退出前必须保存会话。

会话导出仅包含所选设备在会话固定窗口内的记录，最多 8192 条。新 JSON 上限 24 MB（含原有最多 4096 个进程样本、1000 个事件、256 个锚点 / 断点及设备记录）；schema 1 保留 8 MB 读取限制。写入失败或超限保留原文件。打开的磁盘记录也落入独立有界临时存储，程序总会话数继续限制为 64。

## 本机验证与证据

本机为 Windows 11 x64 / Python 3.12.6，依赖按现有锁文件安装。详细硬件、实际路径和原始设备记录只保存在被 Git 忽略的 `artifacts/stage-four/`。

- 修改前回归：249 passed；原版只读启动成功。
- 新增回归覆盖：加权延迟、无请求与零延迟、窗口交集、缺口、容量、重复时间戳、设备变化、只读重开、旧 schema、损坏输入、时钟跳变与睡眠夹具、真实采集子进程超时、Qt 鼠标场景标记。最终结果见 `final-tests.txt` 和 XML。
- `live-disk-load.json`：自建临时文件负载，本机 PDH 磁盘读写记录。测试不修改进程调度。
- `perfmon-reference-long.json`、`perfmon-comparison-long.json`、`perfmon-comparison-long-summary.json`：Windows Get-Counter 与采集器使用相同计数器，约 35 秒重叠区间的均值差异约 0.3%–3%。独立采样边界和背景 I/O 不完全相同，这只是短时一致性验证。
- 40 秒探测中，采集调用均值约 0.37 ms、最大约 0.67 ms；该探测进程句柄保持 369。CPU 时间包含初始化，不能直接当作持续采集 CPU 百分比。
- `ui-validation/`：真实 Qt 鼠标/键盘输入驱动只读界面，监控验证程序自身，检查场景标记、保存/重开完全一致、亮暗主题与 1280×860 / 1040×700 逻辑尺寸。本机缩放为 200%。开关采集和隐藏窗口的 CPU、RSS、句柄与 GUI 定时器数据见 `result.json`；这是短时检查，不是数小时稳定性证明。
- `packaged-smoke/` 与 `packaged-helper.json`：本地脏构建 EXE 的只读启动及内置采集子进程，来源清楚标注为测试构建。

## 后续边界

首个目标游戏已选定为《三角洲行动》，场景为用户指定的实际对局。本机已取得 PresentMon 2.6.0 / v2 metrics / QPC 的真实 CSV 及同步会话。首轮及关闭 GPU 计时的补采都存在大量 ETW 事件丢失和低覆盖，暂只用于格式、对齐与缺失语义开发，不作为有效性能实验；下一步先解决采集质量。原始证据与详细结果保存在本地 `artifacts/stage-four/DELTA_FORCE_SAMPLE.md`，不提交游戏记录。

第三轮增加前台状态同步观察：120 秒内 118 个状态采样点均为游戏在前台，但 CPU 帧区间覆盖仍仅约 86.32%，日志报告 1020333 个 ETW 事件丢失。该结果不足以把此前缺口归因于用户切出；应先排查采集链路，再安排补采。状态为离散采样，不证明采样点之间始终未切换。

用户随后选择停止真实采集，优先开发；不再把取得有效游戏样本作为开发前提。已有样本用于格式、对齐、低覆盖和事件丢失提示验收，不作收益证据。

4.1–4.4 的首版功能已接通；真实设备拔插、系统睡眠和长时间运行仍需后续人工/持续验证。4.4 使用合成记录完成功能验证，不代表真实效果验收。没有测量真实游戏收益，也没有向真实游戏或 ACE 应用策略。

## 4.3 离线帧文件导入

- 明确支持 PresentMon 2.3.0 及 2.6.0 `--v2_metrics` 已核对的普通帧表头；未知/扩展格式、坏行、重复和乱序时间戳原子拒绝。版本是用户声明，并不从表头推断二进制版本。
- 后台解析 CSV，32 MiB / 100000 行 / 64 个流；独立 SQLite 临时存储（2 MiB 缓存、64 MiB 数据库上限），单次运行最多 300000 条帧记录。用户明确选择进程和交换链，禁止默默拼流。
- QPC 使用会话首个锚点线性映射并检查其他锚点残差，用户确认同机同次启动；相对 CPUStartTime 毫秒使用手动首帧偏移，误差未知。CSV 不能验证进程创建时间，不把 PID / 名称匹配宣称为实例核验。
- 显示时间使用 CPUStart + DisplayLatency 定位，DisplayedTime 为驻留时长；CPU FrameTime 为起点间隔。各自计算窗口交集覆盖和缺口，完整区间内帧计算中位数、最近秩 P95/P99、严格超过用户阈值的长帧。跨时钟断点排除，采样结束以后的区间不计。
- 可选导入原采集日志，仅保存日志哈希、报告的 ETW 丢失数与开始/结束完整性标记。不提供日志、日志为空或未正常结束时明确标为未知；低覆盖、断点、手动对齐、日志丢失均有说明，不补零或自动宣称有效收益。完整性标记不证明日志与 CSV 来自同一次采集，仍由导入者确认来源。
- 原实验保留，创建独立只读分析副本。schema 3 携带所选流原始值和来源/映射/对齐/阈值，保存重开重新验证与计算统计；兼容 1 / 2。完整 CSV 有 metadata 和 frame_sample 行。
- `tests/test_frame_recording.py` 覆盖独立副本、损坏导入、资源上限、多流、PID 不匹配、QPC/手动偏移、边界/空交集、显示定位、时钟断点、日志未知/丢失、旧 schema 和 Qt 实际输入。
- `tools/validate_frame_import_ui.py` 只使用夹具和可选已有文件，不启动监控或新采集。已验证导入按钮、异步解析、选择流、创建副本、保存重开、CSV 导出与 1280×860 / 1040×700 亮暗布局。证据见本机 `artifacts/stage-four/frame-import-validation/`。
- 既有实际对局样本在新版导入器中收到 16370 帧，CPU 区间覆盖约 86.32%，显示驻留覆盖约 4.17%，1020333 个 ETW 事件丢失提示保留。来源路径、游戏数据与报告均留在被忽略的 artifacts，不提交仓库。

字段依据：[PresentMon 2.6.0 选项](https://github.com/GameTechDev/PresentMon/blob/v2.6.0/README-ConsoleApplication.md)、[v2 字段语义](https://github.com/GameTechDev/PresentMon/blob/v2.3.0/README-ConsoleApplication.md#csv-columns)。

## 4.4 多轮配对汇总

- `core/repeated_experiments.py` 对每个已结束会话的 before / after 做配对，再按轮等权汇总差值中位数、MAD、范围和有效轮数。相对变化单独统计有效非零基线数；不拼接所有帧，不把单轮帧数当独立重复数。
- 场景、硬件、应用版本、条件声明，加上策略、基线/应用后实际设置、拓扑、采样配置、物理盘身份、窗口时长、工具与指标口径共同分组；缺声明明确排除。测试来源与观察来源分组隔离。
- 状态、应用回读、基线、缺失/覆盖、断点、帧 ETW 日志、对齐方式和磁盘身份分别检查。默认门槛 95% 覆盖 / 3 轮，可见可调；帧附件原门槛不被汇总设置降低。同源分析副本或同实例重叠窗口全部排除，避免选择顺序影响计数。
- 多轮项目独立于实时 History，声明与选择不会修改原会话。项目包含原始快照，重开重新校验/计算；汇总 CSV 保留已选排除轮次和原因。上限 64 轮、300000 原始帧、64 MiB 文件；原子保存失败保留旧文件。
- `core/repeat_demo.py` 生成六轮合成数据，前三轮 CPU P95 为 20→16、20→20、20→24 ms，各轮帧数不同但等权得到中位差 0 ms、MAD 4 ms、范围 -4..4 ms。第 4 轮覆盖 50%、第 5 轮中断排除；版本 2.0 独立组只有 1 轮，标记轮数不足。测试数据标识贯穿界面和导出。
- `ui/repeated_experiments.py` 提供指标选择、门槛、逐轮勾选、声明、测试示例、项目重开及 CSV 导出。示例和项目解析在后台，SQLite 临时资源在创建线程中显式清理。
- `tests/test_repeated_experiments.py` 覆盖全部 18 个指标、分组隔离、未知声明、零基线、重复/重叠、阈值、质量排除、篡改缓存重算、保存失败保留原文件和真实 Qt 操作。
- `tools/validate_repeated_ui.py` 完成“汇总按钮→合成示例→保存/重开”的 Qt 实际输入验收；覆盖亮/暗和 1280×860 / 1040×700 主窗口条件。监控线程未启动、原 History 为空、调度接管数为 0。原始证据、截图、示例项目与 CSV 在本机 `artifacts/stage-four/repeated-validation/`。
