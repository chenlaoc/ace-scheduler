# ACE Scheduler 使用指南

## 一次实验的流程

1. 启动工具和游戏，在“运行概览”的进程表或右上角选择要观察的进程，例如 SGuard64.exe。多个同名进程会分别显示，每个占一行。
2. 打开“实验对照”，选择运行中实例，设置基线／过渡／实验段时长（默认 60／3／60 秒），点击“开始基线”。等待显示“等待应用策略”。这一步只记录，不会修改设置；没有进程时仍可编辑策略。
3. 打开“调度策略”，勾选目标名称，统一选择“较强 / 温和 / 默认”，或直接修改各行的参数。
4. 点击“应用勾选”。每行的参数会用于所有同名进程；本次运行期间，以后发现的同名新进程也会应用。选择预设只会修改草稿，点击“保存勾选”才会保存规则；这两步都不会修改进程的调度值。
5. 到“运行概览”确认实际值和操作结果，回到“实验对照”等待过渡期和固定实验段结束。应用部分失败时保留失败事件，不把它当作正常 After。提前应用、设置变化或后台中断都会标注。
6. 比较均值、采样峰值、有效覆盖和区间累计估算。点击“保存 JSON”保留可重新打开的完整会话，或“导出 CSV”供分析。会话保存在本次运行内，退出程序前请保存；没有持续自动落盘。
7. 结束实验时，在“调度策略”点击“恢复勾选规则”，或在“设置与日志”点击“恢复全部原设置”。程序会恢复该进程第一次被修改前记录的实际值，包括 EcoQoS 的“系统管理”状态；上次异常退出后留下的记录也可以恢复。

规则按完整的 `.exe` 文件名匹配，不区分大小写，也不根据路径判断程序身份。添加自定义规则时请确认文件名，因为所有同名程序都会匹配。

### 停止、退出和恢复有什么区别

点击“停止自动应用”、禁用规则或删除自定义规则，都会停止后续管理，**已经设置的调度值会保留**。要改回原来的值，请使用“恢复全部原设置”。Default 是一组固定参数，选择它不会恢复之前的设置。

关闭窗口时，如果仍有可恢复的进程，可以选择恢复后退出、保留当前设置后退出，或取消退出。恢复失败时，窗口会保留，并在日志中显示原因。

如果程序异常退出，下次打开时会提示有未完成的修改，由你选择是否恢复，不会自动应用或恢复。恢复记录会保留到下一次运行；系统重启后或超过 30 天的记录会归档，不再用于恢复旧进程。

如果其他程序改过同一项设置，程序会保留当前值并提示冲突。可以在设置页选择覆盖并恢复，也可以保留当前设置、放弃全部恢复记录。记录损坏或版本不受支持时，程序会暂停新的调度修改，可先将这些记录归档。

若状态显示“已暂停 · 恢复记录待确认”，设置可能已经改变，但恢复日志尚未确认。该实例会停止后续应用与维护，即使当前值符合策略、再次点击应用或重启工具，也不会解除暂停。请先尝试恢复原设置；遇到冲突时，在设置页明确选择覆盖恢复或保留当前设置并归档记录。归档会放弃全部实例的恢复记录。处理后需要再次点击应用才会启用规则。

“已验证”表示本次请求的字段均成功；“无需修改（已验证）”表示这些值原本已符合目标；“部分成功”会列出失败或不支持而跳过的字段。它们描述本次操作，不保证 Apply Once 之后没有外部程序修改设置。

## 调度预设与动态 CPU 选择

### 只调整一个字段

Priority 下拉框可以选择“不修改”；CPU 分配窗口中可以勾选“不修改 CPU 分配”；EcoQoS 下拉框提供“不修改 / 系统管理 / 开启 / 显式关闭”。例如只试 EcoQoS，先将 Priority 和 CPU 分配设为“不修改”，再选择 EcoQoS 的目标状态，点击“预览勾选…”核对，最后应用。

“不修改”表示本次策略不接管该字段，不会为它读取原值、写入设置或创建新的恢复记录；正常监控仍会读取并展示当前状态。此前已改过的值不会因为选择“不修改”而恢复，已有恢复记录也会保留。要还原这些字段，请使用“恢复原设置”。三个字段都选“不修改”时，不打开调度写入句柄，结果显示“未修改（全部字段均不接管）”。

“预览勾选…”显示当前勾选规则的草稿、解析后的本机逻辑 CPU ID、停用或不支持的字段及维护方式。预览不会保存配置或应用策略。默认预设仍是下面的一套固定参数，与“不修改”和“恢复原设置”含义不同。

| 预设 | Priority | Affinity | EcoQoS |
| --- | --- | --- | --- |
| Default | Normal | 全部可用逻辑 CPU | OFF |
| Mild | Below Normal | 最后 25%，向上取整，至少 2 个，不超过可用总数 | ON |
| Strong | Idle | 最后 1 个可用逻辑 CPU | ON |
| Custom | 用户选择 | 用户选择 | 用户选择 |

Priority 提供 Idle、Below Normal、Normal、Above Normal、High；不提供 Realtime。提高优先级可能增加与其他程序的竞争，实验通常从较温和的配置开始。

启动时通过 `psutil.cpu_count(logical=True/False)` 获取核心数，并通过 Windows 活跃 Processor Group 数量、总活跃处理器数、系统 Affinity mask 检查逻辑 CPU ID。不会从“物理核心 × 2”推导线程数，也不会把本工具自身可能已经受限的 Affinity 当作整个系统的 CPU 列表。物理核心数取不到时显示“未知”。

预设从当前可用 ID 的有序列表计算，支持不连续 ID；“最后 1 个/2 个”仅指逻辑处理器编号，不代表 P-Core 或 E-Core。没有根据编号猜测核心类型。为后续 `GetSystemCpuSetInformation` / `EfficiencyClass` 拓扑扩展保留了独立模块。

25%/50% 表示选取的逻辑处理器数量比例，**不是 CPU 用量百分比硬上限**。例如 16T 的 Strong 选择 `[15]`，24T 选择 `[23]`，无需更改源码或配置。单逻辑 CPU 机器的 Mild 自动降为一个 CPU。

系统存在多个 Processor Group，或逻辑处理器数超过 64 时，显示“当前版本仅支持单 Processor Group”，禁用 CPU 选择和 Affinity 写入。仍可打开 CPU 分配窗口选择“不修改”；这样只应用 Priority 或 EcoQoS 时，不会因未请求的 Affinity 而显示部分成功。若仍请求 Affinity，则结果明确标注不支持、已跳过。不会把跨组编号拼成错误掩码。64T 单组通过无符号指针宽度掩码支持第 63 位。

## Apply Once 与 Keep Enforced

- Apply Once：对每个 `PID + create_time + name` 实例，每次点击应用只尝试一次。进程重启后出现的新实例重新应用。
- Keep Enforced：周期性回读并仅在不符合策略时写入，包括 EcoQoS。采样默认 1 秒，维护默认 3 秒；两个后台计时器独立，支持 1/2/3/5/10 秒。
- 权限不足、API 不支持或部分失败时明确显示原因。没有待确认恢复记录时，Keep Enforced 失败后至少等待 30 秒再尝试；也可手动点击应用重试。有待确认记录的实例须先处理恢复，两个计时器都不会继续重试。
- 修改并保存已生效规则会停止该规则的自动应用，点击应用后才启用新策略。每次重启工具都回到仅监控状态。

## EcoQoS 的含义

使用 `Get/SetProcessInformation(ProcessPowerThrottling)`，只控制 `PROCESS_POWER_THROTTLING_EXECUTION_SPEED`。ON 设置 ControlMask 和 StateMask 对应位；OFF 保留控制位并清除状态位；恢复时按原始状态恢复该位，同时保留无关的节流位。

策略中的“系统管理”清除该机制的控制位和状态位，将决定权交还系统；“显式关闭”保留控制位、清除状态位。“不修改”完全跳过该字段。三者并不等价。无论选择哪一种目标，其他节流机制的位都会保留，恢复时使用该实例原先记录的状态。

界面显示 ON、OFF、“系统管理”或“未知”。“系统管理”不等于 OFF；未知/不支持也不会被当成关闭。EcoQoS 是 Windows 的节能调度提示，Windows 11 之前对应 LowQoS，既不承诺固定频率，也不保证任务管理器的“效率模式”标识完全等同于这个单独设置。[微软文档](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-setprocessinformation)

## 监控指标与实验限制

CPU% 表示进程占整机 CPU 的比例，范围为 0 至 100%。计算时，用进程 user+system CPU 时间差除以实际经过的单调时钟时间，再除以系统逻辑处理器数。因此，在有 N 个逻辑 CPU 的机器上，一个逻辑 CPU 满载约显示为 100/N%，与 psutil 原生可能超过 100% 的进程 CPU% 不同。RAM 是工作集，MB 按十进制计算，即 1,000,000 字节。

Read/Write MB/s = 两次 `psutil.Process.io_counters()` 字节差 / 实际秒数 / 1,000,000。Total Read/Write GB 是进程自启动累计值 / 1,000,000,000，并非工具启动后累计。read_count / write_count 在采样和 CSV 中保留。首次采样、权限拒绝、计数器回退和跨应用边界的首个采样周期均不伪造速率，显示 `—`，曲线留空。峰值是采样区间平均速率的最大值，不能捕捉小于采样间隔的所有瞬时尖峰。

这些数据来自 **Windows 进程级 I/O 计数器**，包含文件、网络和设备等 I/O。缓存、预读，以及活动被计入其他进程或内核驱动等情况，都会影响它与实际磁盘读写的对应关系。因此，这个数字不能当作 SSD 的物理 NAND 读取量，也不能用来判断 SSD 寿命是否变化。[psutil 说明](https://psutil.readthedocs.io/stable/#psutil.Process.io_counters)

CPU 调度限制不等于磁盘限速，I/O-bound、异步 I/O、缓存命中或内核完成的工作可能不受预期影响。进程优先级仅影响调度竞争，系统空闲时 Idle 仍可运行。工具不承诺降低读峰值、修复 SSD SMART 错误或改善游戏体验。ACE/游戏的受保护行为也可能拒绝修改或对延迟作出反应；不保证兼容或不会引起游戏报错。建议使用相似场景重复对照，记录操作是否实际成功；不要把不同扫描阶段的差异直接解释为因果关系。

运行概览仍显示最近 60 秒。实验会话有独立 ID，固定 Before／过渡／After 窗口；观察段结束后样本与统计不再滚动变化。直接应用策略也会自动建立会话，使用此前最多 60 秒作基线、3 秒过渡和 60 秒实验段。基线依据实际读取的设置核验，不把 Default 预设当作原值。

再次应用会新建会话；旧观察未结束时标记中断，已完成的对照仍保留。恢复追加到对应会话，保留逐字段成功、失败或冲突结果，不覆盖原对照；只恢复旧日志而没有本次应用时，建立“仅恢复记录”。维护定时器产生的写入、重置、失败，以及采样间隔变化、计数器回退、后台停止也会记录。进程重启使用新的创建时间和实例身份，不拼接数据。

实验页有“运行中实例 / 已结束实例 / 实验会话”入口，不依赖概览的当前进程。最多保留 64 个会话，不自动删除旧实验；达到上限后需先保存并移除旧会话才能继续新建。每会话最多 4096 个样本、1000 个事件，触及上限会明确标注。普通滚动历史另保留最近 16 个退出实例，不影响已建立的会话。

JSON 包含会话状态、实例、目标路径及可读取的文件版本、工具构建信息、实际基线、请求策略、逐字段操作结果、拓扑和采样设置、原始样本及事件。缺失或无法读取的文件版本保留为 null。“打开 JSON…”只打开快照，不启用任何规则，也不继续给旧快照追加采样。实验文件包含真实进程名称、PID、路径和设置，与脱敏诊断文件不同。

CSV 的 `row_type` 区分 `metadata`、`sample`、`event`。元数据行的 `context_json` 包含完整策略、实际值、窗口及各指标统计／缺失区间；样本行保留原始 `sample_seconds` 和参与该阶段的 `window_overlap_seconds`；事件行保留结构化结果。边界样本可分配到相邻阶段，按交集时长统计，不能把重复投影的完整采样时长相加。过渡期不计入前后对照。空值代表缺失，不代表零。

平均值和 P95 按有效区间时长加权；峰值仍是采样区间平均速率的最大值。累计 MB 按速率乘窗口交集时长估算，跨边界时假设该采样区间内速率均匀，不能还原区间内部的突发。覆盖率的分母为计划窗口，缺失区间与尚未采集部分都不当作零。UTC 使用记录开始时固定的单调时钟偏移换算，属于近似对齐。物理磁盘指标和外部帧时间记录不在本阶段实现。

## 界面主题

打开“设置与日志 → 外观”，可选择亮色、暗色或自适应（跟随系统）。选择后立即生效并自动保存，下次启动仍使用同一选项。旧配置默认自适应；系统主题无法识别时使用亮色。固定选择亮色或暗色后，系统主题变化不会改变应用外观。

切换主题会更新页面、图表、窗口按钮及应用内对话框，不会应用或停止规则，也不会清掉草稿和实验数据。若配置保存失败，会提示原因并保留原来的主题。系统控制的 UAC 安全桌面不受应用主题设置影响。

## 配置与日志

`%APPDATA%\ACE-CPU-Scheduler\config.json` 保存规则、优先级、EcoQoS、维护模式、采样/维护间隔、窗口位置。预设保存语义，例如：

```json
{
  "mode": "last_n",
  "count": 2,
  "percentage": 25,
  "minimum": 1,
  "cpus": []
}
```

只有 Custom 保存具体 ID；换机器后过滤不存在的 ID，若一个也不剩，明确阻止应用并要求重新选择，不会写入零掩码。配置通过临时文件和原子替换写入。损坏/不兼容配置备份为 `config.invalid-*.json`，本次使用默认监控配置并在界面提示。

规则总数最多 256 条，包含 5 条内置规则。手工配置缺少的内置规则会以禁用状态补齐；补齐后超出上限的配置会被拒绝并保留备份，不会截断自定义规则。

配置格式现在为 `version: 2`。Priority 的“不修改”保存为 `"unchanged"`，Affinity 保存为 `{"mode": "unchanged", ...}`；EcoQoS 使用 `"unchanged"`、`"system"`、`"on"`、`"off"`。旧版 v1 配置加载时会迁移到内存，`true` 转为 `"on"`、`false`（含旧默认值）转为 `"off"`，其他规则参数不变；加载仍然只观察，不自动应用。首次保存前会保留 `config.v1-时间戳.json` 备份，备份失败则不覆盖旧配置。回退旧版程序前，应退出当前程序并用该备份恢复 v1 配置；旧版不能读取 v2。恢复日志格式保持不变。

日志位于同目录的 `scheduler.log`，按 512 KB 轮转，保留两份旧文件；只记录发现、退出、操作、错误等事件，不持续写每秒指标。GUI 日志最多 500 行。日志包含进程名、PID、最终解析的 CPU ID、各项操作结果。每用户使用配置目录锁避免多个实例同时维护策略。

## 权限、托盘与诊断

普通启动会在打开主窗口前申请管理员权限。授权后先观察，点击应用或恢复即可执行，不需要再切换窗口、重复点击。取消 UAC 会结束本次启动。若已有窗口，程序会先尝试唤醒它。

只查看数据时可以使用 --monitor-only，只读模式不会申请管理员权限，也不能修改调度。Windows 的 UAC 提示由系统控制，程序不会绕过或关闭它。配置保存在启动账户的用户目录中；使用其他管理员账户的凭据启动时，会读取那个账户的配置。

关闭窗口默认会退出应用，也可以在设置中改为隐藏到托盘。隐藏后仍会采样和维护已启用的策略，可以从托盘菜单重新打开窗口、停止规则、恢复设置或真正退出。再次启动程序会显示已有窗口；托盘不可用时，窗口也会显示出来。程序不会默认随系统启动。

后台出错后会停止维护并显示原因。处理错误后，可以点击“重新启动后台”。重启后仍只观察，需要继续调整时请再次应用策略。

导出诊断时，先选择 ZIP 的保存位置。文件包含程序版本和构建信息、系统版本、CPU 拓扑数量、去掉进程名称的配置摘要，以及日志中的事件类别、调度字段和错误代码。原始配置、恢复记录和权限切换记录不会放进 ZIP，文件也不会上传。

“关于”页面的版本和许可不联网也能查看。查看更新和反馈问题的按钮会打开 GitHub 页面，需要网络连接。程序不会自动更新，目前也没有代码签名。

v1.7.0 在“实验对照”增加可选物理磁盘记录、场景备注和时间标记。启用磁盘采集并选择设备后开始新基线；旧会话的设备不随下拉框改变。结束后保存 JSON 可跨程序重开，磁盘数据为设备总体负载，不能解释成该进程独占的磁盘负载。真实游戏效果、长时间运行、睡眠恢复和设备断开验证留待后续。使用步骤、指标口径与限制见 [第四阶段进度](STAGE_FOUR_PROGRESS.md)。

选择已结束的会话或打开实验 JSON，在“外部帧时间”点击“导入 PresentMon CSV”。选择 CSV、声明工具版本（2.3.0 或 2.6.0 的 v2 metrics）、可选采集日志，再点击“读取文件”，明确选择与会话 PID / 名称一致的交换链。不会自动启动采集；不同交换链不会合并。

`CPUStartQPC` 文件需要会话中的 QPC 锚点，并由用户确认同机、同次系统启动。CSV 本身不含机器、启动或进程创建时间，不能自动证明这些关系。`CPUStartTime` 文件按毫秒读取，手动指定所选流首帧相对会话开始的秒数（负数为提前），始终标为近似对齐；不根据文件名或修改时间猜时间。其他时间列、v1 / 默认 v3 或扩展帧格式暂不支持。

预览中可调整长帧阈值（默认严格大于 33.333 ms）与覆盖门槛（默认 95%）。CPU 帧起点间隔与显示驻留时长分开统计；后者使用 DisplayLatency 定位显示区间，缺字段时不补零。分位数为逐帧最近秩 P95/P99，中位数使用常规定义；只有完整落入固定窗口的帧参与分位数，覆盖率使用区间交集。跨时钟断点的区间排除，过渡期不计入前后统计。缺口明细保留前 50 段，数量保留全部（小于等于 1 微秒的舍入缝隙不记作缺口）。

点击“创建分析副本”后原会话不变；保存 JSON 包含所选流原始值、来源哈希、声明版本、字段映射、对齐依据和阈值，可脱离原 CSV 重开。完整 CSV 导出增加 `frame_sample` 行，列顺序在元数据 `row_fields` 中。schema 3 兼容读取 schema 1 / 2，旧程序不能打开新格式。

单 CSV 最大 32 MiB / 100000 行 / 64 个流，后台解析并使用临时 SQLite；每次运行最多保留 300000 条帧存储记录。JSON 仍有 24 MB 原子保存上限，超限保留原文件，可改导出 CSV。无日志时丢失情况记为未知；有日志只表示日志报告的事件数，不能当成游戏丢帧数。低覆盖或其他质量问题下的数值仅描述已收到的帧，不代表完整游戏性能，更不证明调度收益。

### 多轮实验汇总

在“实验对照”点击“多轮实验汇总”。已结束会话会作为独立快照加入；勾选要比较的轮次，选择帧、进程或物理磁盘指标。每个会话自身的应用前／应用后组成一对，不跨不同会话自动配对，不把不同轮的所有帧拼在一起。

没有真实数据时点击“载入测试示例”：六轮合成数据包含下降、不变、上升、低覆盖、中断和另一应用版本。示例直接生成测试记录，不查询游戏、系统时钟或设备，不启动采集，也不调用调度 API。窗口、行、原始记录和导出都保留测试标识；观察记录与测试记录不会混为一组。

选中一轮，在下方填写场景、硬件标识、应用版本与条件（路线、画质、限帧、缓存和后台活动等），点击“保存本轮声明”。这些是用于分组的用户声明，不能证明条件真的一致；空白会明确排除，不把未知条件当作相同。声明不修改原会话。分组还比较进程名、策略、应用前后实际设置、CPU 拓扑、采样设置、调度器版本、物理盘身份、观察时长，以及帧工具版本/口径/长帧阈值；详细依据可悬停查看或在项目 JSON 中复查。

默认最低覆盖 95%、至少 3 个有效轮次，界面可调整；帧指标还保留原帧附件的覆盖门槛，取两者较高值。未完成、中断、基线未核验、策略没有成功回读、指标缺失、低覆盖、时钟断点、帧日志未知/丢失、手动对齐、设备身份缺失等轮次会显示原因。相同原实验的分析副本或同实例重叠窗口会全部排除；取消多余副本的选择后再汇总。

只对纳入轮次计算 `after - before`。每轮一票，展示差值中位数、差值的绝对偏差中位数（MAD）、最小/最大差值和有效轮数。负值仅表示所选指标下降，不能直接称为游戏改善。相对变化使用 `(after - before) / before`；基线为零时保留绝对差值，相对变化留空。有效轮数达到门槛不代表统计显著性或因果收益。

“保存项目”会写入各轮原始会话快照、声明、选择和阈值，最多 64 轮 / 300000 条帧 / 64 MiB；超限保留旧文件。再次“打开多轮项目”会重新验证原始会话和重算统计，不信任文件里的缓存报告。“导出汇总 CSV”包含各组以及所有已选择轮次的纳入/排除状态、原因、覆盖率和差值。未选轮次仍保存在项目 JSON 中。数据留在本地，未连接真实采集。
